defects found, reproduced, fixed, and regression-tested.

1. Interrupted identity claim leaves a permanently stuck session
   (network interruption / paths that appear successful but leave
   inconsistent state)

   Repro: OTP verification succeeds (bridgeMsg91SessionAndClaim mints a
   real, provider-verified Supabase session), then the app is
   backgrounded/killed or the network drops before
   claimApprovedB2bIdentity() completes. The user now has a valid session
   with no buyer membership. On every subsequent launch,
   resolveBuyerSession() found customer_buyer_eligible_company_id() null
   and returned 'no_membership' -- routing to SessionRecoveryScreen, whose
   'Try again' button calls resolveBuyerSession() again, which re-checks
   membership but never re-attempts the claim that actually failed. This
   state could never resolve itself; the only way out was realizing you
   had to go all the way back to Welcome and log in again from scratch
   (a fresh OTP), which nothing on the recovery screen suggested.

   Fix: resolveBuyerSession() now attempts claimApprovedB2bIdentity() once,
   speculatively, when company resolution first comes back null, before
   falling back to 'no_membership'. Safe to call speculatively: Core's
   claim RPC (current definition, 20260914160000) is a read-then-
   idempotent-activate operation keyed off the session's own verified
   phone/email -- a no-op for an already-claimed or genuinely-not-a-buyer
   session, exactly like calling it twice in the normal login flow already
   was. 'Try again' on SessionRecoveryScreen now actually has something to
   retry.

2. 'Add to cart' silently overwrites (not adds to) existing cart quantity
   (paths that appear successful but leave inconsistent state, relative to
   user intent/data integrity)

   Repro: add Product A at quantity 5 -> draft cart has 5. Navigate away,
   reopen Product A's detail page later -> the quantity stepper always

   design, matching an edit-quantity flow) sets the line to 1, silently
   destroying the other 4 units the buyer believed were already secured --
   while the UI shows a success toast implying it worked additively.

   Fix: ProductDetailScreen now fetches the current draft on load and
   pre-fills the quantity stepper from the existing line for this product,
   if any (extracted as the pure, tested findDraftLineQuantity() in
